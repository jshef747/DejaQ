This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

DejaQ is an LLM cost-optimization platform that reduces API costs through semantic caching, query classification, and hybrid model routing.

**Cache miss pipeline:** User Query → Context Enricher (Qwen 1.5B, makes query standalone; skipped only when there is no history) → Normalizer (produces cache key; lowercase-and-strip with no model call, except opinion queries which Gemma 4 E2B rewrites to "best \<noun\>") → Cache Filter (heuristics) → LLM gets **original query + history** (preserves tone) → Response to user → Background: Generalize response (Gemma 4 E2B) → Store in ChromaDB (if the filter passes and the generator did not report truncation — see [docs/openai-compat-api.md](docs/openai-compat-api.md))

**Cache hit pipeline:** User Query → Context Enricher → Normalizer → ChromaDB lookup → **trusted hit** (cosine ≤ `DEJAQ_CACHE_TRUST_DISTANCE`, 0.15) served directly, or **band hit** (0.15–`DEJAQ_CACHE_BAND_MAX_DISTANCE`, 0.20), or **lexical rescue** (≤ `DEJAQ_CACHE_RESCUE_MAX_DISTANCE`, 0.60, when word-level alignment confirms a typo'd variant) — band/rescue hits served only if the **Cache Validator** (Gemma E2B checks cached answer covers the new query, aided by a word-mismatch hint) accepts → INVALID → treat as miss → Context Adjuster adds tone (skipped on a **single-turn** request at or under `DEJAQ_ADJUSTER_SKIP_DISTANCE`, 0.075 - no tone gap to close, so the stored answer is served verbatim) → Response to user. Validated band/rescue hits store the typo'd phrasing as an **alias** entry (`alias_of` metadata) so the same typo becomes an instant trusted hit next time; deleting an entry cascades to its aliases. Never for an attachment-anchored hit: `store_alias` copies only the answer, `original_query`, and `user_id`, dropping `file_sha`/`file_kind`/`image_*`, so an alias of one would be an ungated text entry reachable without the attachment ever being sent.

> **Image gate (`/v1/responses` only):** when a request carries an image, the text pipeline runs as usual, but a cache hit is served only if the **image gate** also passes. The gate has two paths, chosen by what the image actually contains:
>
> - **Document** (OCR returns confident text — `mean confidence ≥ 60` AND `≥ 6 words at conf ≥ 60`): compared **by its words**. The word floor is low on purpose: confidence is what separates a document from a photo, and a short crop read well (measured: 9 words at 86.8) is a small document, not something to refuse. Served only when `token overlap ≥ DEJAQ_CACHE_IMAGE_TEXT_MIN_JACCARD (0.85)` against the entry's stored `image_text` **AND** at least `DEJAQ_CACHE_IMAGE_TEXT_MIN_SHARED_TOKENS` (4) shared tokens (`image_text.py:215-216`) — a ratio over a handful of tokens is noise. No identifier rule. It was 0.80, on the evidence that no two different documents exceeded 0.798; that held only until the corpus contained two receipts from one shop, which reach **0.848** (same items, same total, different invoice number and date). 0.85 is the measured zero-merge point over ~1.85M labelled pairs. End-to-end recall is ~10–42% depending on the population and that is the accepted trade. `services/image_text.py`, engine = the `tesseract` binary.
> - **Ambiguous** (≥ `DEJAQ_CACHE_IMAGE_AMBIGUOUS_MIN_WORDS` (4) tokens found but read *below* the confidence floor): **never served and never stored.** These used to fall through to the pixel path, which was the largest single source of wrong answers (1,712 + 204 false merges measured) because two different pages of text look near-identical to CLIP. It matters because only ~11% of real scanned business forms clear the confidence floor. The test is OCR quality, not amount of text — an unreliable read of a lot of text is garbage, a confident read of a little text is a document.
> - **Photo** (little or no readable text): compared **by its pixels** — `CLIP distance ≤ DEJAQ_CACHE_IMAGE_MAX_DISTANCE (0.08)` **AND** `dHash hamming ≤ DEJAQ_CACHE_IMAGE_MAX_HAMMING (15)` against `image_dhash`/`image_clip`. No unguarded trusted tier; both thresholds load-bearing. 0.08 rather than 0.10 because on 812 real photographs a daylight rocky beach and a sunset over water were served as the same image at CLIP 0.0929 / hamming 6. Hamming is what stops the rest: two *different* photographs of one hillside measured CLIP 0.027 and were refused by hamming alone. A near-uniform image (under `DEJAQ_CACHE_IMAGE_MIN_TILE_VARIETY` (10) distinct dHashes over a 4×4 grid) is refused outright — every blank page is the same white rectangle to CLIP. `services/image_fingerprint.py`.
>
>   One leak remains, measured and knowingly left: a scanned form that OCR cannot read *at all* (0–2 tokens) misses the ambiguous rule, which needs 4, and falls to the pixel path — two such FUNSD forms merge at CLIP 0.0648 / hamming 14. Fixing it needs a "looks like a failed document scan" signal, not a threshold.
>
> Once the gate passes, the hit is served differently from a text hit, because every downstream model is blind to the image: the **validator compares question-to-question** (the cached answer is never sent — it is asked only whether both questions ask for the same thing about the verified-identical image) and the **context adjuster is skipped** (image answers are stored verbatim, so no tone was stripped to restore). This is not the same as trusting the distance: numbered-item siblings (`solve part a`/`part b`, 0.0898) sit *closer* than legitimate paraphrases (0.1094), so the embedding cannot separate them and the validator stays load-bearing. Measured 9/9 paraphrases served, 0 reachable false serves, validator 6,468 ms → 577 ms.
>
> Kinds never mix: a photo cannot match a document entry, and a text request matches neither. Raw image bytes are never stored — only fingerprints. On a miss, image requests bypass the difficulty classifier, but capability decides local vs. external the same way it does for files: routed **local**, with the image bytes passed through to Ollama's own `images` field, when the workspace's configured local model reports the `vision` capability (`services/ollama_catalog.py::supports_vision`, a cached `/api/show` call — not `/api/tags`, which is measured wrong for this on the shipped default model) and `X-DejaQ-Routing-Mode: hard_external` isn't set; **external** otherwise. If Ollama rejects an image-bearing local call anyway (the model was swapped after the capability cache's last refresh), the caller gets a specific 422 naming the mismatch instead of the generic apology, and nothing is cached. Without `tesseract` installed, documents degrade to the photo path (a warning is logged; `start.sh` warns at boot). Separate paths exist because pixel similarity is *inverted* for documents: two different courses on one template measured CLIP 0.027 / hamming 0 (would have been served as the same image) while two screenshots of the same syllabus measured hamming 10–19 (would have missed). Border trimming and a digit-token identifier rule were both implemented and **removed** — each helped only the small sample it was derived from. Every threshold here is swept over 286,000 labelled pairs; do not hand-tune them. Measurements: [docs/image-gate.md](docs/image-gate.md); harness: [evals/image_similarity/](evals/image_similarity/). After changing any of them, run `dejaq-admin cache purge-images --workspace <slug>` — entries stored under the old rules may carry fingerprints the new ones would never accept.

> **File gate (`/v1/responses` only):** a request may carry **one** PDF, DOCX, or text/Markdown/code file (`input_file`, data URL only; one attachment total, so image+file is a 400). The text pipeline runs as usual — the file's content never enters the cache key — and a hit is served only if the **file gate** also passes.
>
> The gate is **exact**, and this is the whole design: `sha256` of the whitespace-normalised extracted text, compared with `==`. Do not reach for the image gate's machinery here. That gate needs CLIP, dHash, confidence floors and a swept token-overlap threshold *because OCR is noisy* — two reads of one page disagree, so identity can only be approximated, which is why its constants took ~1.85M labelled pairs to pin down. PDF, DOCX, and text files hand us the text deterministically, so identity is exact, **false merges are impossible by construction**, and there is nothing to sweep: no thresholds, no `evals/document_similarity/`, no `purge-files` command (a sha256 cannot go stale the way a swept threshold can). Normalisation collapses whitespace only — so the same document re-saved by a different producer still matches — and deliberately does *not* fold case. `services/file_text.py`, extraction = `pypdf` for PDF, `python-docx` for DOCX (paragraphs + tables only — headers/footers/comments/tracked-changes/properties are excluded so they don't churn the hash on every re-save), UTF-8 content sniff for everything else (Markdown, plain text, source/config files — no maintained extension list; `.docx` is checked first since it is a ZIP and would otherwise fail the sniff). `DEJAQ_CACHE_FILE_MIN_CHARS` applies only to PDF/DOCX, where extraction can fail silently; text/Markdown/code files have no floor beyond "non-empty after normalisation".
>
> A file whose normalised text is under `DEJAQ_CACHE_FILE_MIN_CHARS` (200) is **never served and never stored** — the same rule as the image gate's `ambiguous` class. This is the **scanned PDF** case: no text layer means no identity, so it is refused rather than guessed at (rasterising to the pixel path would inherit the image gate's measured worst leak). The answer still comes back; there is just no cache entry. Corrupt and encrypted PDFs land here too.
>
> Entry ids for file requests key on `normalized_query + "|file:" + file_sha`. Without the suffix two **different** documents asked the **same** question ("summarise this document" — the question people actually ask) would share one id and overwrite each other. Text entries keep their existing ids.
>
> Serving a file hit follows the image rules exactly, because every downstream model is blind to the attachment: the **validator compares question-to-question** (`attachment_anchored`, shared with the image path — the hash proves the *file* matches, not that the two *questions* want the same thing) and the **context adjuster is skipped** (answers stored verbatim). On a miss, files still bypass the difficulty classifier, but capability decides local vs. external, not the file's mere presence: a file with usable extracted text (`file_doc.ok` — every kind, PDF included) routes **local**, folded into the prompt through `_query_with_inlined_file` (fenced and labelled as untrusted data — reused unchanged from the external path, never a second inlining mechanism); a file with no usable text (a scanned PDF, a corrupt upload) still forces **external**, exactly as every kind did before this existed, so the answer never comes from a silently-blank local extraction. An explicit `X-DejaQ-Routing-Mode: hard_external` remains a policy ceiling above capability. Only the routing decision changed — what each route sends did not: PDF still goes to the external provider as a native document part (richer: keeps tables/layout/embedded images) and only inlines its `pypdf` text for the *local* branch, which has no native-part equivalent and so pays that quality cost; every other kind already inlined the same way on the external branch and now does so on local too. Kinds never mix — a Markdown request cannot match a PDF entry, and neither matches an image or text entry. Raw file bytes are never stored, only the hash. Measurements and rationale: [docs/file-gate.md](docs/file-gate.md).

> **Typo handling:** there is deliberately **no spell correction** anywhere in the pipeline — a dictionary checker mangles jargon and proper nouns ("frnce"→"fence", "itly"→"idly") and poisons cache keys. Instead: *typos change letters, different questions change words*. `services/lexical_match.py::align()` does word-level fuzzy alignment (exact words cancel, leftovers must fuzzy-match, question words never satisfy each other) — 99.1% typo recall / 99.9% sibling rejection ([docs/lexical-match-report.md](docs/lexical-match-report.md)). BGE embeddings absorb single typos in the trusted zone; heavier typos land in the band or the align-gated rescue tier, always behind the validator. The validator prompt carries word-swap few-shots plus the gate's mismatch hint ("'list' vs 'string'"). Phonetic spellings ("duz"→"does") intentionally miss — LLM answers.

## Branching

`staging` is the integration branch: feature branches merge into `staging` first for review and end-to-end testing, and only `staging` merges into `master`. Do not merge feature branches directly into `master`.

**Feature branch workflow:**
1. Create feature branch from `staging` (e.g., `git checkout -b feat/my-feature staging`)
2. Work on the feature and push to the feature branch
3. When ready, request approval (code review, testing, etc.)
4. After approval, merge the feature branch into `staging` and delete the branch
5. Later, `staging` merges into `master` when ready for release

## Commands

### Setup
Run from `server/` — the Python project (pyproject.toml + uv.lock) lives there; there is no root project.
```bash
cd server

# Mac (Apple Silicon) - enables Metal GPU acceleration
CMAKE_ARGS="-DLLAMA_METAL=on" uv sync

# Windows (NVIDIA) - enables CUDA acceleration
$env:CMAKE_ARGS = "-DLLAMA_CUBLAS=on"; uv sync

# CPU only
uv sync
```

### Run
Generation runs through **Ollama** (local or remote). Start Ollama and pull the model tags first:
```bash
ollama serve
ollama pull qwen2.5:0.5b qwen2.5:1.5b gemma4:e2b gemma4:e4b
```

```bash
# Preferred: start from the repo root with stack + Ollama-mode selection
./start.sh

# Stacks: all = backend + dashboard + chat; server = backend + dashboard (no chat);
# client = chat app only (connects to a DejaQ server elsewhere on the network).

# Non-interactive examples:
./start.sh --stack=all --mode=local
./start.sh --stack=server --mode=local
./start.sh --stack=client                    # chat only; set the server in chat Settings
./start.sh --stack=all --mode=remote --ollama-url=http://<host>:11434
./start.sh --stack=all --mode=local --lan   # expose chat (4000) + API (8000) on the LAN
# --lan binds chat + API to 0.0.0.0 so other devices on the same network can reach them;
# dashboard (3000), ChromaDB (8001), and Redis stay localhost-only. The admin API is
# unauthenticated, so only use --lan on trusted networks.

# Manual (Terminal 1) Redis
redis-server

# Terminal 2: FastAPI
uv run uvicorn app.main:app --reload
# Server at http://127.0.0.1:8000
# UI: the chat/ Next.js app (http://localhost:4000)

# Terminal 3: Celery background worker (--pool=solo for single-worker safety)
uv run celery -A app.celery_app:celery_app worker --queues=background --pool=solo --loglevel=info

# Without Redis (fallback mode — generalize+store runs in-process):
DEJAQ_USE_CELERY=false uv run uvicorn app.main:app --reload
```

### Workspace model

DejaQ is multi-**workspace**: you (the operator) are above all workspaces and can create as many as needed. Each workspace owns API keys + provider credentials + LLM routing config; departments are cache partitions within a workspace. The workspace slug is the billing/isolation boundary — departments only segment the cache.

On first launch with an empty DB the dashboard routes to an **onboarding wizard**: create a workspace → department → reveal the one-time API key. The CLI `dejaq-admin workspace create --name <name>` is the headless alternative.

### Control-plane vs data-plane split

| Surface | Bound to | Protected by |
|---|---|---|
| Dashboard (`:3000`) | 127.0.0.1 | Localhost only |
| Admin API (`/admin/v1/*`) | 127.0.0.1 | `AdminLoopbackMiddleware` (403 from LAN) |
| Data plane (`/v1/*`) | 0.0.0.0 (LAN) | Workspace API key |

Remote admin access: `ssh -L 3000:localhost:3000 -L 8000:localhost:8000 user@server-ip` — see [docs/admin-access.md](docs/admin-access.md).

### Management auth (`/admin/v1/*`)

`require_management_auth` always returns an unauthenticated dev-admin context (`ManagementAuthContext.local_dev()`); the dashboard opens with no login. There is no credential to configure — the surface is protected by loopback binding (`AdminLoopbackMiddleware`), not a password.

Bootstrap a workspace + API key with the dashboard onboarding wizard or with:
`dejaq-admin workspace create --name "Acme"` then `dejaq-admin key generate --workspace acme`.

> **Note:** `/v1/chat/completions` and `/v1/feedback` always use DejaQ workspace API keys — the dev-admin context never applies to them, only to `/admin/v1/*`.

| `DEJAQ_ADJUSTER_SKIP_DISTANCE` | `0.075` | **Single-turn requests only** (no prior conversation history): cache hits at or below this cosine distance skip the context adjuster and serve the stored answer verbatim, since there is no tone gap to close. Never applies to a multi-turn follow-up - the enricher folds a genuine "give me the short version" turn back into a restatement of the original question, so distance alone cannot tell that apart from a typo'd repeat (`app/config.py`) |
| `DEJAQ_CACHE_TRUST_DISTANCE` | `0.15` | Trusted-zone cosine ceiling; hits at or below are served directly |
| `DEJAQ_CACHE_BAND_MAX_DISTANCE` | `0.20` | Upper bound of the validator-guarded band; hits in `(trust, band_max]` need validator approval. Set at or below trust distance to disable |
| `DEJAQ_CACHE_RESCUE_ENABLED` | `true` | Lexical-rescue tier: candidates past the band are eligible when `lexical_match.align` confirms a typo'd variant; always validator-gated |
| `DEJAQ_CACHE_RESCUE_MAX_DISTANCE` | `0.60` | Distance ceiling for the rescue tier |
| `DEJAQ_CACHE_ALIAS_ENABLED` | `true` | Alias learning: validated band/rescue hits store the typo'd phrasing as an alias pointing at the same answer |
| `DEJAQ_CACHE_IMAGE_MAX_DISTANCE` | `0.08` | Photo-path CLIP cosine ceiling. 0.10 merged a beach with a sunset (measured 0.0929) |
| `DEJAQ_CACHE_IMAGE_MAX_HAMMING` | `15` | Photo-path dHash hamming ceiling; both this AND the CLIP distance must pass |
| `DEJAQ_CACHE_IMAGE_OCR_ENABLED` | `true` | Route text-bearing images to the OCR document path; `false` sends every image to the photo path |
| `DEJAQ_CACHE_IMAGE_OCR_MIN_CONFIDENCE` | `60.0` | Mean OCR word confidence required to treat an image as a document. Swept 50–80: 0 false merges at every level, so this only routes — the token threshold carries the safety |
| `DEJAQ_CACHE_IMAGE_OCR_MIN_WORDS` | `6` | Words at confidence ≥ 60 required to treat an image as a document; the confidence floor does the real separating, so this stays low — a short crop read well is still a document |
| `DEJAQ_CACHE_IMAGE_TEXT_MIN_JACCARD` | `0.85` | Document path: the only matching threshold. Measured zero-false-merge point once real receipts are in the corpus (two from one shop reach 0.848); lower it for recall (0.80 buys ~10 points at 2 measured merges) |
| `DEJAQ_CACHE_IMAGE_AMBIGUOUS_MIN_WORDS` | `4` | Tokens at which a text-bearing image read BELOW the confidence floor becomes un-cacheable instead of falling to the photo path |
| `DEJAQ_CACHE_IMAGE_TEXT_MIN_SHARED_TOKENS` | `4` | Shared tokens required before an overlap ratio counts as evidence at all |
| `DEJAQ_CACHE_IMAGE_MIN_TILE_VARIETY` | `10` | Distinct dHashes over a 4×4 grid required to fingerprint by pixels; below it the image is too uniform to identify |
| `DEJAQ_CACHE_FILE_ENABLED` | `true` | Kill switch for PDF/DOCX/text file **attachments**, not just their caching: `false` means an attached file is never extracted and never sent to the provider, so the request is answered as if nothing were attached. Images have no equivalent switch |
| `DEJAQ_CACHE_FILE_MIN_CHARS` | `200` | Below this many extracted characters a file has no identity, so it is neither served nor stored (scanned PDFs land here). Not a swept threshold — the populations it separates are nowhere near the line |
| `DEJAQ_MAX_ATTACHMENT_BYTES` | `10485760` | Server-side attachment size cap, applied to files **and** images |
| `DEJAQ_TESSERACT_BIN` | `tesseract` | OCR binary path (`brew install tesseract` / `apt install tesseract-ocr tesseract-ocr-heb`) |
| `DEJAQ_TESSERACT_LANGS` | `heb+eng` | OCR languages; needs the matching `traineddata` installed |
| `DEJAQ_OCR_TIMEOUT_SECONDS` | `20.0` | Per-image OCR timeout; on timeout the image is treated as un-cacheable |

Threshold rationale (why 0.20, 0.60, 0.05, and why images get no trusted tier): [docs/image-gate.md](docs/image-gate.md).

### Endpoints
- `GET /health` — health check; also reports Celery worker status
- `POST /v1/chat/completions` — OpenAI Chat Completions-compatible chat (streaming + non-streaming); **requires** `Authorization: Bearer <workspace-api-key>` (401 when missing/invalid — no anonymous fallback) and optional `X-DejaQ-Department` header; response includes `X-DejaQ-Response-Id` header when cached or stored. Hard queries return HTTP 402 when the workspace has no credential for the configured external provider. A hard-query provider *failure* on the **non-streaming** path returns 400 (request rejected), 502 (the stored provider credential was rejected — deliberately not 401, which on this endpoint means the caller's own DejaQ key was rejected), or 429 (provider rate limit), each carrying a fixed per-status message naming the provider and never the provider's own error text; a status-less failure (timeout, connection reset) and every streaming failure still return 200 with the generic apology. On a **streaming** miss the response head is flushed before generation starts and the deltas are the generator's own output; the id header therefore names the entry the request intends to store, which a store guard can still refuse - contract and its consequences in [docs/openai-compat-api.md](docs/openai-compat-api.md).
- `POST /v1/responses` — OpenAI Responses API endpoint (newer recommended format). Same auth (401 without a valid workspace API key) and `X-DejaQ-*` headers. Body: `{model, input: string | [{role, content}...], instructions?, stream?, temperature?, max_output_tokens?}`. Non-streaming: `{id, object:"response", output:[...], output_text, usage:{input_tokens, output_tokens, total_tokens}}`. Streaming: typed SSE events (`response.created`, `response.output_text.delta`, `response.completed`, etc.). `previous_response_id` / `conversation` rejected with HTTP 400 — DejaQ is stateless; clients send full history in `input`. The `chat/` Next.js app is the reference client. **Images:** an `input_image` content part (data URL only; remote URLs rejected 400) attaches one image (>1 image → 400). Image requests bypass the difficulty classifier on a miss, but route local when the workspace's configured local model reports the `vision` capability (a cached Ollama `/api/show` check, `services/ollama_catalog.py::supports_vision`) and `X-DejaQ-Routing-Mode: hard_external` isn't set; external otherwise. A local call Ollama rejects anyway (model swapped after the capability cache's last refresh) surfaces a specific 422 naming the mismatch, not the generic apology, and is never cached. The cache serves an image hit only when the text pipeline hits AND the image fingerprint gate passes (see below). **Files:** an `input_file` content part (data URL only) attaches one PDF, DOCX, or text/Markdown/code file; one attachment total, so >1 file or image+file is a 400, and an attachment over `DEJAQ_MAX_ATTACHMENT_BYTES` is a 400. PDF and DOCX are recognised by MIME or extension; anything else is recognised by attempting a strict UTF-8 decode of its bytes — no maintained MIME or extension list, so a `.py`/`.json`/`Dockerfile`/etc. attachment is accepted regardless of what MIME the client sent. A type `file_text.kind_for` cannot identify this way (not PDF/DOCX by MIME-or-extension, and not valid UTF-8) is a 400 naming what arrived and what's accepted — checked at parse time, so a recognised-but-unreadable file (scanned/corrupt PDF, corrupt DOCX) is unaffected and still answered without a cache entry. File requests also bypass the classifier on a miss, but route local when extraction produced usable text (every kind, PDF included — inlined into the prompt behind the same delimiter Markdown always used) and external when it did not (a scanned/corrupt file — same "answered, never cached" outcome as before) or `X-DejaQ-Routing-Mode: hard_external` is set; only the external route ever sends PDF as a native document part, since that has no local equivalent and is richer than its extracted text. The cache serves a file hit only when the text pipeline hits AND the file's exact hash matches. Only `/v1/responses` accepts attachments — `/v1/chat/completions` stays text-only. **Sticky attachments:** an attachment must be re-sent on every turn it is relevant to. The `chat/` app therefore keeps one **pinned** until the user unpins it, and sets `X-DejaQ-Attachment-Sticky: true` on the carried turns. A follow-up sent *without* the attachment is a plain text request: the model answers from history alone, and its answer is stored as an ungated text entry that a different document could later match — the gates only protect the turns that actually carry the file. The header itself is diagnostic (it appears in the `file kind=` / `image kind=` logs as `carried-over` vs `freshly-attached`); nothing branches on it.
- `POST /v1/feedback` — thumbs-up/down feedback on a cached response; requires `Authorization: Bearer <workspace-api-key>`; body: `{"response_id": "<X-DejaQ-Response-Id value>", "rating": "positive"|"negative", "comment": "<optional>"}`; first negative deletes entry, subsequent negatives decrement score by 2.0; positive increments score by 1.0. **Edit & Save** rides the same request: add `edited_answer` (requires `rating: "positive"` + `interaction_id`, else 422) and the human text becomes the cached answer *and* takes the +1.0, in one call. The reply adds `edit_status` (`saved` | `created` | `not_cached` | `message_mismatch`) and the `response_id` the edit actually landed on — adopt it, since an alias-served id redirects to its root and a created entry is keyed by a freshly derived query. The old answer is discarded everywhere it was copied: the entry is overwritten in place (score, hit counts and any attachment fingerprints kept), its aliases are rewritten, every model store path refuses to write over an `authored="human"` entry, and the context adjuster is skipped on serve so the next asker gets the text byte-identical. Human entries are exempt from score eviction; a thumbs-down still deletes them. `messages` is only needed to create an entry that does not exist yet, and must be **withheld for attachment turns** — the replay is blind to the file, so those turns can only overwrite an existing gated entry ([docs/openai-compat-api.md](docs/openai-compat-api.md))
- `/admin/v1/*` management endpoints — **loopback-only** (127.0.0.1); auth is an unauthenticated dev-admin context — no token is required:
  - `GET /admin/v1/whoami`
  - `GET|POST|DELETE /admin/v1/workspaces[/{slug}]`
  - `GET /admin/v1/departments`, `POST|DELETE /admin/v1/workspaces/{workspace_slug}/departments[/{dept_slug}]`
  - `GET|POST /admin/v1/workspaces/{workspace_slug}/keys`, `DELETE /admin/v1/keys/{key_id}`
  - `GET /admin/v1/stats/workspaces`, `GET /admin/v1/stats/workspaces/{workspace_slug}/departments`
  - `GET /admin/v1/model-catalog/providers` and `GET /admin/v1/model-catalog/providers/{key}/models` - the LiteLLM-backed catalog (`app/services/model_catalog.py`): every `mode == "chat"` model in `litellm.model_cost`, minus `STRUCTURED_CREDENTIAL_PROVIDERS` (Azure/Bedrock - no field for their multi-part credential). The provider-list endpoint returns key + model_count only; models are fetched per provider, never all at once (the full catalog is 349 KB). This is what `llm_config_service._validate_and_resolve_external_model` validates `external_model` against and what the dashboard's Settings picker reads: a `<select>` grouped into "configured for this organization" / "all providers" optgroups, and an `<input list>` + `<datalist>` for the model (native type-to-filter; a free-typed model not in the datalist is still accepted, subject to the same server validation). Supersedes the old `GET /admin/v1/providers` (`app/services/provider_registry.py`'s hand-maintained allowlist), deleted in migration stage A1c once the dashboard picker no longer called it
  - `GET|PUT /admin/v1/workspaces/{workspace_slug}/llm-config` - `external_model` is validated on write against the LiteLLM catalog above (rejected 422 naming the fix if LiteLLM cannot address the model, or if it resolves to a `STRUCTURED_CREDENTIAL_PROVIDERS` provider) and its provider is recorded into `external_provider` alongside it, rather than guessed at request time; PUT `null` clears both. `routing_threshold`, and (per-workspace pipeline model selection) `local_model`, `generalizer_model`, `adjuster_model`, `enricher_model`, `normalizer_model`, `validator_model`, plus (per-workspace prompt editing) `enricher_system_prompt`, `normalizer_system_prompt`, `validator_system_prompt`, `validator_image_system_prompt`, `adjuster_system_prompt`, `generalizer_system_prompt`, `local_model_system_prompt`, plus (per-workspace token budgets) `default_max_tokens`, `rewrite_max_tokens`, `ollama_num_ctx` — each mirrors the global default of the same name (lowercased) in `config.py` (`DEFAULT_MAX_TOKENS`, `REWRITE_MAX_TOKENS`, `OLLAMA_NUM_CTX`); all nullable, PUT null to reset to the shipped default. A blank (empty or whitespace-only) `*_system_prompt` is rejected 422 — null is the only way to clear one. The six pipeline `*_model` fields are validated on write against a live `GET /api/tags` call to the configured Ollama host (any installed tag, not just ones registered in `MODEL_RUNTIME_SPECS`) — a name Ollama doesn't currently report is rejected 422 naming the offending value. A workspace override later uninstalled from Ollama (day-2 drift, uncatchable at write time) is caught at request time instead: `OllamaBackend`'s 404 is turned into `ModelNotFoundError` and the affected role (any of the six) falls back to its shipped default and logs a warning, rather than a raw 500 — one shared `model_backends.complete_with_default_fallback()` so a newly overridable role cannot ship without it. The three token-budget fields are validated on write for the RELATIONSHIP between them, not just individually: `rewrite_max_tokens` must be at least 2x `default_max_tokens` (the rewrite prompt carries the whole raw answer) and `ollama_num_ctx` must be at least 2x `rewrite_max_tokens` (the context window has to hold the rewrite's own generation plus the prompt carrying the answer being rewritten), and `default_max_tokens` must exceed 1024 — the exact value measured to truncate ordinary answers mid-sentence. A rejected combination is judged against the EFFECTIVE resulting triple (existing stored values for any field this update doesn't touch), not just the fields present in one PUT — see `llm_config_service._validate_token_budget_overrides`. `ollama_num_ctx` also has a hard ceiling of `config.OLLAMA_NUM_CTX` itself (32768 as shipped) - one window is sent to every Ollama-backed role, so the bound is the SMALLEST maximum among the models sharing it (`qwen2.5:1.5b`, on the enricher and adjuster), which is exactly the value that constant already encodes; the override can therefore only lower the shipped window, never raise it. That ceiling bounds the other two transitively

## Architecture

Layering: `routers/` (endpoints) → `services/` (business logic) → `schemas/` (Pydantic models) → `db/models/` (ORM) → `db/*_repo.py` (DB access). Grep for a filename rather than expecting a per-file index here.

| Directory | Holds |
|---|---|
| `app/main.py`, `config.py`, `celery_app.py` | FastAPI init + CORS + health, centralized settings, Celery broker/queue config |
| `app/routers/` | `openai_compat.py` (`/v1/chat/completions`, plus the shared `run_chat_pipeline`), `feedback.py`, `departments.py`, `admin/` (`/admin/v1/*`) |
| `app/routers/openai_responses.py` | `/v1/responses` — its own router (`openai_responses.py:199`, mounted at `main.py:90`); parses `input`/attachments, then delegates into `openai_compat.run_chat_pipeline` |
| `app/services/` | The pipeline: `normalizer`, `context_enricher`, `context_adjuster`, `validator`, `cache_filter`, `classifier`, `lexical_match`, `memory_chromaDB` (semantic cache), `image_fingerprint` + `image_text` (image gate), `file_text` (PDF/DOCX/text file gate), `rag_service` + `rag_ingest` + `rag_admin_service` (RAG knowledge layer). Plus infra: `model_backends` (OllamaBackend + `MODEL_RUNTIME_SPECS`), `service_factory`, `llm_router`, `external_llm` + `llm_providers/` (the shared LiteLLM transport), `model_catalog` (the LiteLLM-backed model/provider catalog), `credential_service`, `admin_service`, `stats_service`, `llm_config_service` + `pipeline_config_cache` (per-workspace pipeline model and system-prompt overrides) + `ollama_catalog` (installed-tag discovery), `feedback_service`, `request_logger` |

| `app/middleware/`, `app/dependencies/` | Bearer token → workspace/department resolution onto `request.state` |
| `app/utils/` | `logger.py`, `exceptions.py` (`ExternalLLMError` / `…AuthError` / `…TimeoutError`), `db_freshness.py` (SQLite mtime signal shared by the in-process TTL caches) |
| `cli/` | `dejaq-admin` (workspace, dept, key, cache, stats, rag) + Rich rendering helpers |

**Key patterns:**
- All generation runs through Ollama (`OllamaBackend`); `service_factory` builds one shared backend from `DEJAQ_OLLAMA_URL` (local or remote)
- `MODEL_RUNTIME_SPECS` maps logical role names (e.g. `gemma_e2b`) to Ollama tags (e.g. `gemma4:e2b`)
- The DeBERTa difficulty classifier and BGE cache embeddings are the only in-process ML (torch); generation is not in-process
- All schemas use Pydantic BaseModel
- Client sends full message history in the `messages` array (stateless; no server-side conversation store)
- Cache miss triggers background generalization + storage via Celery task queue (falls back to in-process if Celery disabled) — only if cache filter passes
- Celery workers reach the same shared Ollama endpoint for generation (no per-worker model loading)
- Context enricher rewrites follow-up queries ("tell me more") into standalone questions before normalization
- Cache filter skips storing trivial messages (filler words, too short, too vague)
- Per-request stats logged to SQLite (fire-and-forget via asyncio.create_task)
- Feedback adjusts ChromaDB entry scores (+1.0 positive, −2.0 negative); first negative deletes immediately
- A human-edited answer (Edit & Save) is stored verbatim under `authored="human"`: never generalized, never re-adjusted on serve, never score-evicted, and never overwritten by a model answer. Every store path checks the same `memory_chromaDB.is_human_authored` before writing — the Celery generalize-and-store task, its in-process fallback in `openai_compat.py`, and the thumbs-down escalation store in `escalation.py` — so a fourth store path cannot ship without the guard
- External LLM routing supports any single-API-key LiteLLM provider through encrypted workspace credentials - not a hand-kept list: `llm_providers.is_usable_provider(provider)` (`llm_providers/provider_keys.py`) accepts a DejaQ provider key when it maps (through the three renames - `google`->`gemini`, `together`->`together_ai`, `fireworks`->`fireworks_ai`) into `litellm.provider_list` and isn't one of `model_catalog.STRUCTURED_CREDENTIAL_PROVIDERS` (Bedrock/Azure, which need more than one credential field). Every usable provider is served through one shared `LiteLLMTransportClient` (`llm_providers/litellm_transport.py`), built lazily and cached per provider on first use by `external_llm._PROVIDER_CLIENTS`/`_client_for`. `ExternalLLMService` is a singleton
- `ExternalLLMRequest.temperature` defaults to `None` and is sent to a provider only when the client explicitly set one — never inject a hardcoded default here. Claude Opus 4.7+/Sonnet 5 and every `gpt-5.x` model 400 on any non-default `temperature`, and that 400 used to be swallowed into a generic HTTP 200 apology (`openai_compat.py`), so a workspace on an affected model looked like it simply had a cache that never filled. `anthropic.py`/`openai.py` each retry once without `temperature` on a 400 that names it; a provider 400/429 now reaches the caller as that same status on the non-streaming path, and a rejected provider credential as 502 (streaming has already flushed its 200 headers by the time generation starts, so it still gets the apology there). The body is a fixed per-status message, never the provider's own text — that text can echo a masked form of the stored credential, and this body goes to any holder of a workspace API key, so the raw message stays in the log
- Workspace/dept/API-key data lives in SQLite (SQLAlchemy + Alembic); `dejaq.db` by default

### Management API

`/admin/v1/*` is a separate operator surface from the OpenAI-compatible `/v1/*` gateway. Its authentication is unconditional: `require_management_auth` always grants an unauthenticated dev-admin context. The surface is protected by loopback binding, not by a credential. See [Management auth](#management-auth-adminv1) above.

The workspace API-key middleware skips `/admin/v1/*` before parsing or logging `Authorization`, so admin tokens are never treated as customer API keys.

## Deployment Modes (Ollama local / remote)

All generation runs through Ollama — `--mode=local` uses `http://127.0.0.1:11434`, `--mode=remote` takes `--ollama-url` (see the Run section for both invocations). The DeBERTa classifier and BGE cache embeddings still load in-process (torch) on first request. ChromaDB starts with the app stack; Redis backs Celery (or set `DEJAQ_USE_CELERY=false` to run background storage in-process).

FastAPI stays lightweight and sends independent async HTTP requests to Ollama; total throughput is bounded by the Ollama host. For external (hard-query) provider credentials set `DEJAQ_CREDENTIAL_ENCRYPTION_KEY` (back it up; losing it is unrecoverable).

## Test Harnesses

Offline eval harnesses live under `evals/` (`enricher`, `normalizer`, `adjuster`, `validator`, `image_similarity`). There is deliberately **no** file/document harness — the file gate matches on an exact hash, so it has no threshold to sweep ([docs/file-gate.md](docs/file-gate.md)). Image-gate thresholds are derived by `evals/image_similarity/protocol.py` over a labelled corpus — never by hand. Invocations, metrics, datasets, and per-config results: [evals/README.md](evals/README.md). Generated `reports/` are gitignored.

The generalizer prompt is re-resolved inside the Celery worker for the same reason its model is. Editing the Context Adjuster or Generalizer prompt invalidates the calibration of their runaway/looping safety-net thresholds (measured against the shipped prompts specifically), which is why the Pipeline page shows a warning on those two stages. Per-workspace **token budget** overrides ship on the same Pipeline page: three nullable integer columns on `workspace_llm_configs` (`default_max_tokens`, `rewrite_max_tokens`, `ollama_num_ctx`), each mirroring a global default in `config.py` and each field shown with the current effective value as its placeholder so an empty field reads as "using the default." Server-side validation enforces the RELATIONSHIP between the three (rewrite budget ≥ 2x answer budget, context window ≥ 2x rewrite budget, answer budget > 1024 - the value measured to truncate ordinary answers) rather than just per-field bounds, because a too-low generation cap produces no error anywhere: the store guard at `openai_compat.py` correctly refuses to cache a truncated answer, so the cache just quietly stops filling. `finish_reason` is now recorded per request (`requests.finish_reason` in the SQLite stats DB) and the resulting truncation rate (truncated ÷ miss requests - a cache hit is never truncated) is surfaced in dashboard Analytics next to the existing hit-rate/latency/tokens-saved tiles, which is what makes that failure mode visible at all. Semantic cache (ChromaDB — trusted tier at cosine ≤ 0.15, validator-guarded band 0.15–0.20, align-gated lexical rescue ≤ 0.60, and alias learning that stores a validated band/rescue phrasing as an `alias_of` entry so it becomes an instant trusted hit next time), Background generalize+store on cache miss, Context Enricher v5 (Qwen 1.5B, 88.7% @0.15 across 5 datasets; the regex gate is an eval-only variant in `evals/enricher/configs/v2_regex_gate` and was never promoted into `context_enricher.py`), Smart Cache Filter (skip non-cacheable prompts), Difficulty Classifier (NVIDIA DeBERTa — routes easy→local, hard→workspace credential backed provider), Celery + Redis task queue (non-blocking generalize+store), OpenAI-compatible endpoint with API-key auth + per-department cache namespacing, Workspace/department/API-key/credential management (SQLAlchemy + Alembic SQLite + `dejaq-admin` CLI), Stats tracking (SQLite + Rich CLI — `dejaq-admin stats`), Score-based cache eviction (Celery beat), Feedback API (score adjustments + delete on first negative), Edit & Save (a user corrects a served answer and the correction becomes the cached answer under `authored="human"` — one `/v1/feedback` call that both stores the text and applies the thumbs-up; `services/answer_edit.py`), Web dashboard (Next.js) with local dev-bypass auth, Ollama-only generation (local or remote via `OllamaBackend`/service_factory — decouples inference from FastAPI for multi-user parallelism). DeBERTa classifier + BGE cache embeddings run in-process (torch). Hard-query runtime credentials come from encrypted `workspace_provider_credentials`. Image caching on `/v1/responses` (one image per request; routed local or external by capability and difficulty, not an unconditional external bypass - see the routing notes below and "Attachments are classified for difficulty like text" in AGENTS.md): documents matched by OCR text (Tesseract) on a swept token-overlap threshold plus a shared-token floor, photos by CLIP+dHash, and text-bearing images that miss the document bar refused outright — CLIP embedder runs in-process (torch), OCR shells out to `tesseract`. Thresholds derived over ~1.85M labelled pairs across seven corpora (coursework, DocUNet, FUNSD, arXiv, SROIE receipts, Rico screenshots, INRIA Holidays photos, UHDM screen recaptures); expect roughly 10–42% end-to-end recall depending on the population, which is the measured ceiling for this approach.
Image requests answered locally when the local model can see: the cache-miss classification step now asks `ollama_catalog.supports_vision` (a cached `/api/show` call against the workspace's configured local model, never `/api/tags` - measured wrong for this on the shipped default model) and routes local, passing the image bytes through Ollama's `images` field (`model_backends.py`, `LLMRouterService`), when it reports `vision` and `X-DejaQ-Routing-Mode: hard_external` isn't set; external otherwise, exactly as before. The capability cache has a staleness window (an admin can swap the workspace's local model in Ollama between refreshes), so a local call is also guarded at the wire level: `OllamaBackend` recognises Ollama's rejection of an image-bearing call to a non-vision model (`LocalVisionUnsupportedError`, matched by status code - 400 or 500 - on a call that carried images, not by Ollama's exact error text, which is version-dependent) and the router surfaces it as a specific 422 naming the real cause, never the generic apology, and never cached. No answer-quality eval was built for this - the captain explicitly deferred it; routing here is capability-based only, not quality-based.
File caching on `/v1/responses` (one PDF, DOCX, or text/Markdown/code file per request): identity is an exact sha256 of the extracted text, so there are no thresholds, no eval harness and no false merges; PDF/DOCX files without a readable text layer (scanned PDFs, corrupt DOCX) are refused rather than guessed at, while text/Markdown/code files have no such floor since decoding them is exact.
File attachments answered locally: a file with usable extracted text (every kind, PDF included) now answers from the local model instead of forcing the external route unconditionally — the machinery (`file_text.py` extraction, the `_query_with_inlined_file` fenced-inlining helper) already existed and was simply never wired to the local generation branch. The external branch is unchanged: it still sends PDF as a native document part (richer — keeps tables/layout/embedded images) and inlines every other kind behind the same data delimiter it always did. Local PDF answers pay a known, real cost — table/layout/embedded-image loss, since they come from `pypdf`'s plain-text extraction alone — stated here so it isn't rediscovered by surprise. A file with no usable text (a scanned PDF, a corrupt upload) still forces external exactly as before, so the answer is never fabricated from a silently-blank local extraction; `DEJAQ_CACHE_FILE_MIN_CHARS` still gates caching only, not answering. `X-DejaQ-Routing-Mode: hard_external` remains a policy ceiling above file capability, same as it already was for text queries.
RAG — per-workspace knowledge layer ([docs/rag-layer.md](docs/rag-layer.md)): admins curate documents (pasted text, PDF/DOCX/text/code uploads, URLs, OCR'd images) into a workspace's own `{slug}__rag_kb` ChromaDB collection, kept separate from the volatile Q→A cache and never score-evicted. On a cache miss, the closest chunks (within `DEJAQ_RAG_MAX_DISTANCE`) are injected into the prompt as fenced DATA and answered by the routed local/external model; the retrieved text never enters the cache key. Managed via the dashboard **Knowledge Base** page, `dejaq-admin rag`, and `/admin/v1/workspaces/{slug}/rag-documents`. Ingestion reuses `file_text`/`image_text`; there is no edit action — re-adding identical content replaces by sha256, changed content is a new document.
Multilingual difficulty classifier decides routing (`dejaq-classifier-probe-multilang` investigation, `dejaq-classifier-wire-in` wiring, `dejaq-classifier-cutover` cutover): a frozen `sentence-transformers/LaBSE` embedding + a `LogisticRegression` head trained on 770 labelled items across seven languages (`app/services/labse_classifier.py`) decides `easy`/`hard` for every text request's "classify" step, every language, no per-language branching - see `DEJAQ_LOAD_LABSE_CLASSIFIER`/`DEJAQ_LOAD_LEGACY_CLASSIFIER`/`DEJAQ_LABSE_CLASSIFIER_THRESHOLD` above. This also replaces the Hebrew-specific routing judge (`HEBREW_ROUTING_ENABLED`, `_judge_hebrew_hard` - both removed): Hebrew falls through the same classify step as every other language. The old NVIDIA-DeBERTa classifier (`ClassifierService`) is not loaded by default - it has no job left once routing moved to LaBSE - but stays in the tree behind `DEJAQ_LOAD_LEGACY_CLASSIFIER` since `staging` still routes off it. Live-measured through the real server: `הוכח שיש אינסוף מספרים ראשוניים` (prove there are infinitely many primes) now scores hard at 0.7522 and routes external, where the old classifier scored it easy at 0.1293 and missed it (0/44 hard-Hebrew caught on the `dejaq-classifier-probe-multilang` corpus) - this is the regression the cutover closes. Matched memory A/B on this machine (`vmmap -summary <pid> | grep "Physical footprint"`, same process, only `DEJAQ_LOAD_LEGACY_CLASSIFIER` toggled): legacy classifier not loaded measured 2.7GB at startup / 4.0GB warmed; loaded measured 3.2GB / 4.5GB - not loading it is a real ~0.5GB savings, not just memory-neutral. Loader reuses `classifier._select_device` (CUDA → MPS → CPU), so the MPS gap noted below now applies equally to both classifiers.

## Dashboard

The web dashboard lives in `dashboard/` (Next.js 16, TypeScript, Tailwind v4, App Router). It talks to the management API at `/admin/v1/*`. Setup and env vars: see [dashboard/README.md](dashboard/README.md).

> ⚠️ Next.js 16 differs from older versions — see [dashboard/AGENTS.md](dashboard/AGENTS.md). Notably the middleware file convention was renamed `middleware.ts` → `proxy.ts`; the dashboard has no middleware file of either name, since local mode never gated dashboard access.

**Auth:** dev bypass only. The dashboard skips login entirely; `lib/api.ts` sends `Authorization: Bearer dev-local` on every `/admin/v1/*` call, and the backend ignores the value (`require_management_auth` always grants a dev-admin context). `/v1/chat/completions` and `/v1/feedback` always use DejaQ workspace API keys, never the dashboard's own auth.

**CORS:** FastAPI must allow `http://localhost:3000` (`allow_origins` in `server/app/main.py`) for local development.

## Chat App

The chat client lives in `chat/` (Next.js, App Router - see the Run section above for its dev server and stack flags). It never mirrors: the interface chrome (sidebar side, layout, English labels) stays left-to-right always, and direction is decided per rendered text, not for the whole app, since a conversation can mix Hebrew and English turns. `app/components/text-direction.ts` picks `ltr`/`rtl`/`auto` by counting Hebrew/Arabic vs Latin characters rather than using the browser's native `dir="auto"` directly - that heuristic looks only at the first strong character, which misreads a Hebrew sentence opening with a Latin acronym ("REST API הוא..."). Applied per rendered block (message body, conversation title, composer, answer editor, RAG chips) rather than to a whole markdown answer at once, because a code sample's English tokens would otherwise skew the count for the surrounding prose - see the `directional()` wrapper and `plainText` re-export in `ChatMessage.tsx`/`CodeBlock.tsx`. Code blocks are force-`ltr` in `globals.css` regardless of the answer's direction, since code is never Hebrew.
